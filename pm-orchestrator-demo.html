The Problem

The mockup gap costs real time

Before a developer writes a line of code, a PM or designer needs to sketch what the feature looks like. Today that process is manual, disconnected from the codebase, and produces throwaway artifacts.

Before Manual process

  • PM writes ticket → shares in Slack → someone picks it up
  • Designer opens Figma, starts from scratch or adapts a template
  • No access to actual component library — invents colors, fonts, spacing
  • First version misses real column names, status values, action labels
  • 2–4 revision cycles before it matches the real app style
  • Mockup becomes stale the moment a developer starts working
  • Total time to acceptable mockup: 4–8 hours per feature

After PM Orchestrator

  • PM pastes a JIRA ticket ID into the tool
  • Tool reads the ticket + crawls the live app + analyzes the codebase
  • Generates a mockup using real Quasar components and actual CSS
  • Real column names sourced from Vue component tableFields()
  • Real status values from domain STATUS_COLOR_MAP
  • Refine with a sentence: "add a filter chip for SLA breach"
  • Total time to acceptable mockup: 2–5 minutes per feature
Product Requirements

What it must do

Functional requirements grouped by capability. All requirements implemented and shipped.

JIRA Integration

  • Fetch ticket by ID from Atlassian REST API v3
  • Parse Atlassian Document Format (ADF) to plain text
  • Extract linked URLs — Figma, Confluence, web links
  • Scrape and embed linked URL content into prompt
  • Fall back to mock data when credentials absent

Codebase Analysis via MCP

  • 17 MCP tools — routes, components, GraphQL, store, AST graph
  • Persistent HTTP MCP server on port 3100 (warm code graph)
  • Resolve $t('key') i18n labels to English text
  • Extract real tableFields() column definitions
  • Domain-specific status color maps from source constants
  • Batch multi-file reads to reduce round-trip latency

Capture Grounding

  • Playwright crawler snapshots live Manager Dashboard
  • Captures compiled Quasar CSS bundle + DOM templates
  • Post-crawl analysis classifies pages by archetype
  • CSS injected inline into mockup for iframe rendering
  • Page template catalog embedded in system prompt

Mockup Generation

  • Pure HTML mode: standalone HTML + CSS + vanilla JS
  • Vue/Quasar mode: real components via UMD CDN
  • Real-time SSE streaming to browser
  • HTML rendered in sandboxed iframe
  • LEAN_MOCKUP_RUN: max 3 MCP rounds before HTML output

Refinement Loop

  • Unlimited refinement iterations on a generated mockup
  • Injected CSS stripped before refinement, re-injected after
  • File + screenshot attachment support
  • Optimized refinement prompt — 17k fewer tokens vs generation
  • Each iteration versioned in session history

Session & Observability

  • Sessions persisted to localStorage by ticket ID
  • Per-session dual log: human-readable .log.md + .log.json
  • Token usage + cost per model logged per session
  • All MCP tool calls captured in debug log
  • Full system prompt + user message stored for replay
System Design

Two processes, one pipeline

The tool runs as two separate processes that work together. Next.js builds the prompt and streams the output. A persistent MCP server keeps the code graph warm.

30-Minute Demo Script

Step by step

Each block is a self-contained unit. The highlighted blocks are the live moments — prepare a real JIRA ticket that has good description content before the demo.

0:00 Context — What we're solving
2 min

Open with the status quo, not the tool. Make the audience feel the problem before you show the solution.

  • →
    Show a real JIRA ticket — a medium-complexity UI feature (listing page, new filter, status column addition)
  • →
    Ask: "How long would it take to sketch this in Figma so a developer knows what to build?" — pause for answers
  • →
    Answer: "We do it in under 90 seconds, reading your actual codebase."
Key line: "Every Figma mockup you've seen for Manager Dashboard was built from scratch. This tool builds from the code that's already running."
2:00 Architecture — Two slides maximum
3 min

Show the architecture section of this document. Point at two things only: the Claude CLI subprocess and the MCP server.

  • →
    The browser sends a ticket ID → Next.js fetches ticket, builds a system prompt, spawns Claude CLI
  • →
    Claude CLI connects to port 3100 (the MCP server) — a persistent process with your codebase already loaded in memory
  • →
    Claude reads the real Vue components, GraphQL files, and status maps — then writes HTML
  • →
    The HTML streams back to the browser and renders in an iframe
Avoid: deep-dive into LEAN_MOCKUP_RUN, context caching, i18n resolution. Those are for Q&A. Keep architecture to the 30-second version here.
5:00 Live Demo — First generation
8 min ★ LIVE

The centrepiece. Have the browser open at localhost:3000 before you start. Pre-pick a ticket with good description content and subtasks — avoid tickets with only a one-line description.

  • ★
    Type the JIRA ticket ID in the gateway field and hit Initialize
  • ★
    While the generation screen is animating: narrate what's happening — "Claude is calling the MCP server right now, reading the outbound listing component"
  • ★
    Watch the thinking stream scroll — point out the tool calls: get-page-template, find-related-context
  • ★
    When the mockup appears — let the audience see it for 15 seconds before talking
  • ★
    Point out: nav bar color, table structure, status chip colors, the real column names from the codebase
  • ★
    Switch to History tab — show the generated analysis text and effort estimate alongside the mockup
Key line: "Those column names — 'Audit Details', 'Priority & Deletable After' — came from reading Audit.vue's tableFields() with the i18n keys resolved. No one typed those."
13:00 Quality review — Compare with real app
3 min

Side-by-side if you have a browser tab of the real Manager Dashboard open. If not, use product screenshots from src/mcp-context/.

  • →
    Open the mockup in full-page view (the expand icon in the toolbar)
  • →
    Point at: navy nav bar, filter pill, table header colors (#F6F6F6), sticky first column, pagination bar format
  • →
    Acknowledge what isn't pixel-perfect yet — the crawler grounding makes it closer, but it's a starting point, not a finished design
Key line: "This is the real Quasar CSS that's running on your live instance — we crawled it, stored it, and injected it here. The font and the table chrome are exactly what the real app renders."
16:00 Refinement — Iterate in plain English
4 min ★ LIVE

Type a refinement that makes a visible change. Keep it concrete — not "make it better" but a specific layout or data change.

  • ★
    Suggested prompt: "Add a red SLA Breach warning badge next to the Audit SLA column header, and highlight breached rows in a light red background"
  • ★
    While it generates: "Refinement sends only the existing HTML back — Claude edits it directly. No MCP tools, no codebase reads. It's faster."
  • ★
    When it arrives: point at the change. Show that everything else stayed intact.
  • ★
    Do one more: "Change the section banner stats to show: Total: 72 | Breached: 8 | In Progress: 15"
Key line: "The refinement prompt is 17,000 tokens smaller than a fresh generation. We strip the design docs and keep only the BASE CSS rules — Claude only needs the current HTML and the change."
20:00 Vue / Quasar mode — Real components
4 min ★ LIVE

Switch the mode toggle in the header from "HTML" to "Vue / Quasar" and regenerate the same ticket.

  • ★
    Show the toggle: "This changes the output format from pure HTML to a page that uses Vue 2 + Quasar 1 UMD loaded from CDN"
  • ★
    Regenerate — the generation takes the same time but Claude writes <q-table>, <q-chip>, <q-btn>
  • ★
    Point out the interactive behaviors: hover states on buttons, Quasar's built-in ripple effects, proper tooltip rendering
  • ★
    View source of the iframe (right-click → Inspect in the iframe) — show the Vue instance, the Quasar brand config
Key line: "In HTML mode we're simulating Quasar with our own CSS. In Vue mode, that IS Quasar 1.20.1 — the exact version your production app runs. A developer could take this file and drop it into the codebase as a starting point."
24:00 Observability — Logs and cost tracking
3 min

Switch to the Usage tab. Then open a terminal and show the log files.

  • →
    Usage tab: show input/output tokens, cost in USD, model used for this session
  • →
    Terminal: cat ~/claude-ui-designs/logs/GM-XXXXX-*.log.md — show the step-by-step log with MCP tool calls listed
  • →
    Open the .log.json — "This is machine-readable. You can grep tool calls, measure round-trip times, replay sessions for debugging"
  • →
    Show cost: "A Haiku 4.5 generation is typically $0.002–0.004. Sonnet is 4× that. You pick the model per ticket."
27:00 What's next + Q&A
3 min

Close with honest scope and open the floor.

  • →
    Current: listing pages are the strongest output. Forms and dashboards work but need more refinement
  • →
    Planned: capture crawler re-run automation when app deploys, component library updates for new domains
  • →
    Possible: export generated Vue files directly into the codebase as a PR starting point
  • →
    Open for questions — the architecture diagram is visible for reference during Q&A

Demo Setup Checklist

Before you present

Run through this 10 minutes before the demo starts. Most failures happen because the MCP server wasn't running.

01

Environment

Copy .env.example → .env.local. Set MD_REPO_ROOT to your manager-dashboard path. Set JIRA credentials.

cp .env.example .env.local
02

Dependencies

Install packages. Requires Node 18+. The MCP SDK ships Express as a transitive dependency — no extra install needed.

npm install
03

Start both servers

Single command starts the MCP server (port 3100) AND Next.js (port 3000) via concurrently. Wait for both to show "ready".

npm run dev
04

Warm the index

Hit the MCP health endpoint. First run builds the AST index (~20s). Wait for indexReady: true before demo.

curl :3100/health

Pre-demo ticket selection

✓ Good demo tickets
  • Outbound/Inbound listing page feature
  • New column / filter addition to existing table
  • Status badge or SLA indicator
  • Has >3 acceptance criteria in description
✗ Avoid for demo
  • One-line description tickets
  • Backend-only tickets (no UI)
  • Tickets with only image attachments
  • Deeply nested sub-domain routes not yet crawled
